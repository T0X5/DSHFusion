# 阶段 3.3：统一入口 —— **先划清「兼容」与「派生」**

> 这份不是设计文档，是**前置条件**。
> [PRODUCT-DIRECTION §10](PRODUCT-DIRECTION.md) 把 3.3 定为 **(b) 自研协议兼容的桥**，
> 而 (b) 会踩 [DSHA-PROVENANCE-AUDIT §4](DSHA-PROVENANCE-AUDIT.md) 的失效条件。
> **所以第一批产物是这条界线，不是接口。**

---

## 一、为什么需要界线（一句话）

**端点名与语义必须一致**（不然所有客户端全不兼容），
而 `/app/help` 那份清单文本**就是 `HttpShellService` 里的** ——
**「接口一致」与「实现派生」之间没有天然的分界，必须人为写下来。**

---

## 二、三条判据（可逐项套用）

| | 可以照抄 | 必须自己写 |
|---|---|---|
| **① 名字** | 端点路径、参数名、错误码**标识符** | 错误码的**说明文字**、提示语、任何整句 |
| **② 行为** | 请求 → 返回 → 错误码的**实测对应关系** | 怎么路由、怎么鉴权、怎么限流、怎么缓存 |
| **③ 依据** | **真机实测**（发一次请求，记下返回） | 读 `HttpShellService` 的源码 |

> **判据 ③ 是最要紧的一条。**
> 它在说：**允许从「观察到的行为」反推契约，不允许从「别人的实现」推出契约。**
> 理由很实际 —— 从行为反推会得到**更少**的信息（只得到你测过的那部分），
> 而从源码照抄会得到**全部**信息，包括你并不需要、也说不清为什么要那样写的那部分。

### 一条自我检查

> **如果某段实现「只能照它的写法才写得出来」，停下来记一笔，回头核对 §4。**
> 那可能就是 (b) 正在退化成 (a) 的信号。

---

## 三、已经实测到的协议事实（**都是我自己跑的，不是读来的**）

| 事实 | 怎么得到的 |
|---|---|
| 桥在 `127.0.0.1:3090` | 真机请求 |
| `BRIDGE_PROTOCOL=3` | `GET /app/version` 的返回 |
| `BRIDGE_AUTH=header-x-token` | 同上（**接口自述了鉴权方式**，这一条可以直接用） |
| 凭据在 `/root/.dsh/.bridge_token`，经 `X-Token` 头传 | 实测 + 与 `.bridge_headers` 逐字节比对 |
| 鉴权**不接受** query 里的 token | 我方宿主的兼容垫片就是为此存在的（它把 `?token=` 改写成头） |
| 错误词的**语义族**：`POLICY_BLOCKED` / `EXECUTION_UNKNOWN` / `NO_PERMISSION` / `DISABLED` / `UNAUTHORIZED` | 真机返回 + 端点自述 |

### ⚠️ 一条实测反例，它证明「不能读文档」

`/app/help` 列了 `/app/vscreen/status`，但没有列它的错误码。
实测（本机，只读端点）：

```
GET /app/vscreen/status  →  HTTP 200
{"result":"{\"ok\":false,\"error\":\"VSCREEN_NOT_RUNNING\"}"}
```

**`VSCREEN_NOT_RUNNING` 不在那份清单里的任何一枚错误码里。**

⇒ **端点的自述清单不是穷举。** 所以 3.3 的兼容性依据**只能是实测**，
而且**要对着本机装的那个版本测**（手机上是 `APP_CODE=170`，比我们的审计副本旧一版）。

## 四、这条界线怎么被强制（不是靠自觉）

| 手段 | 挡什么 |
|---|---|
| **端点契约表**（下一批产出）：每行 = 端点 + 实测请求 + 实测返回 + 错误码，**附一条真机调用记录** | 挡「没测就写进契约」 |
| **`dsha-imports.json` 的既有机制** | 一旦 3.3 真出现了从 `HttpShellService` 派生的代码，它必须登记；未登记 = 下次同步静默丢失 |
| **来源审计 §4 的前向引用** | 触发即要求重做逐 blob 溯源 |

---

## 五、这一阶段**不做**什么

- **不决定授权与默认值**（已在 3.2）。
- **不动 DSHA 的代码**（硬约束 1）。
- **不承诺端点数** —— 下一批按「3.1 台账 + 3.2 档位」**只做需要的那部分**，
  不做「把 bridge 的端点全实现一遍」。**那是仿造，不是统一入口。**

---

## 六、下一批

1. 按 3.1 的 11 条能力 + 3.2 的档位，**选出真正要暴露的端点子集**（预计远少于全部）。
2. 为子集里每个端点写**实测契约表**（每行一条真机调用记录）。
3. 只在那之后才谈「入口怎么呈现」—— 呈现属于交互，契约属于接口，**先接口后交互**。

---

## 七、端点子集（**第二件产物**，2026-10-17）

**实测**：`/app/help` 的正文里出现 **30 个**端点路径（清单本身不全，见 §三 的反例）。
但**子集不该按清单划，该按 3.1 的 11 条能力 + 3.2 的档位划**。

### 选择规则（一句话）

> **只为 3.1 台账里的能力开端点；清单里其余的一律不开。**
> 「桥有」不构成理由 —— **那正是仿造与自研的分界。**

### 保留（**8 组**）

| 组 | 端点 | 对应能力 | 档 |
|---|---|---|---|
| 元信息 | `/app/version`、`/app/help` | 特性检测（**必须**：判版本用 `>=`，不能用 `==`） | T0 |
| 屏幕 | `/app/ui/dump`、`ui/screenshot`、`ui/tap`、`ui/input`、`ui/key`、`ui/swipe` | `device.computer-use`、`ui.a11y.drive` | T2 |
| 应用 | `/app/apps`、`/app/launch` | `device.app.control` | T1 |
| 通知 | `/app/notify` | `ui.notify.turn-end` | T1 |
| 悬浮 | `/app/overlay` | `ui.overlay.status` | T1 |
| 虚拟屏 | `/app/vscreen/*` | `device.vdisplay` | T3 → **默认关** |
| 提权 | `/exec?cmd=` | `device.shell.command` | T3 → **默认关**，且按通道分别确认 |
| 交互 | `/app/ask` | 让 agent 能**问用户**（3.1 台账里没有，但**没有它就无法拒绝** —— 见下） | T1 |

> ⚠️ **`/app/ask` 是唯一一个「台账里没有、却必须开」的端点。**
> 理由不是功能，是**安全**：3.2 的 T2/T3 都要求「每次确认」，
> 而**没有 `/app/ask` 就没有「确认」这个动作可做**。
> **不开它，分级就只是一张表。**

### 暂缓（**不是排除**，列明条件）

| 组 | 为什么现在不做 |
|---|---|
| `/app/readfile`、`/app/export` | 文件读写**不属于设备能力层**，属于工作区。混进来会把「统一入口」变成「大杂烩」 |
| `/app/clip`、`/app/share`、`/app/open` | 都需要一个「用户在场」的前提，而 3.2 还没为它们定档 |
| `/app/location`、`/app/sensor(s)`、`/app/torch` | 硬件读取，3.2 里还没有对应档位；**先有档位再谈端点** |
| `/app/plugins` | 它是**上报**通道（插件向 App 报状态），不是能力 |
| `/app/device` | 信息性接口。**但它很可能是 `/app/version` 之外第二个该开的** —— 留到下一批判断 |

### 永不开

`/app/vscreen/touch`（连续触控，`stroke` 为十六进制序列）——
它把**原始触控注入**暴露出去，而 3.1 的 11 条能力里**没有一条需要它**。
`computer-use` 用 `tap`/`swipe` 就够；**「够用」和「能注入原始流」之间要站在够用那一侧。**

### 这个子集的规模 —— **不给手算的数字**

**保留 8 组；暂缓 11 条；永不开 1 条。**（按上面两张表数出来的条目，
不是「清单 30 条减去保留」这种手算 —— 而两者本来也对不上：
`/app/overlay` 与 `/exec?cmd=` **不在**那 30 条里，`vscreen` 的子路由在那 30 条里的只出现一部分。）
