## 未验证的项（如实列出）

| 项 | 为什么没验 |
|---|---|
| **「覆盖更新失败 → 自动回切」** | 🔴 **这条先前被错报成 ✅。** 那个 ✅ 的依据是**恢复**事务的回切 —— 验的是另一个东西。**「受管更新」根本没做**（4 个更新事务类未搬），所以**没有更新可失败**。现定为**阶段 2.8**，见 [PHASE2.8-MANAGED-UPDATE.md](../PHASE2.8-MANAGED-UPDATE.md) |
| `stop` / `daily` 模式的自动备份真的到点跑了 | 只验了界面与设置能保存；**心跳到点自动执行**没等到（15 分钟周期，需要长时间观察） |
| 调度胶水的进程重启后重登记 | 同上 |
| 恢复后 DSH 能**读回**全部会话内容 | 只验了「会话文件回来了、DSH 重启后还在」；**内容逐条比对**没做 |
| `settings.yaml` 的字段级凭据排除 | **前提是错的** —— DSH 0.2.0-rc.2 不用 `settings.yaml`。改而发现的是桥接凭据风险，见 [PRODUCT-DIRECTION 第八节](../PRODUCT-DIRECTION.md) |

## 与记录的偏差

- **标准 4 曾是不成立的**，而且是在验收**之后**才发现的：`CredentialFileBackupSource`
  **从来没有接上生产路径**（全库只被它自己的单测引用），真机上 API Key 明文进了归档 ——
  见 `docs/INCIDENTS.md` 第 41 条。**「验收通过」与「实现正确」是两件事**：
  当时那次验收用的归档里恰好没有会话记录，所以那条泄漏没被触发。
  修复后**重跑**了标准 4 并留下了上面那条证据。
- **标准 5 曾两次以为过了**：第一次是空目标目录（`merge` 与 `replace` 在空目录上无法区分），
  第二次才建了一个应当被删除的会话 —— 见第 44 条。

## 这次验收留下的、比结论更重要的东西

**6 个 bug（第 39–44 条）全部是真机抓到的，而本机 176 条测试 + 335 项套件 + CI 全绿时一个都没抓到。**

其中第 44 条的教训最贵：**14 条恢复测试全部用空目标目录** ——
在空目录上「合并」与「替换」**不可区分**。那不是代码错了，是**测试场景缺了一个维度**。
