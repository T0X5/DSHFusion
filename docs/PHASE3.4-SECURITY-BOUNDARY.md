# 阶段 3.4：安全边界

> **输入**：3.2 的五档默认值 · 3.3 的端点子集 · 3.1 的证据等级。
> **输出**：3.5（真机验证）的**验收清单** —— 3.4 如果说不出「怎么验它真的发生不了」，
> 那它就只是承诺。

---

## 一、边界的定义方式：**说「不可能」，不说「不允许」**

「不允许」是策略，「不可能」是结构。两者的差别在这里：

| 说法 | 能被什么推翻 |
|---|---|
| 「T2 默认是关的，所以不会读屏」 | **一个忘了判断的代码分支** |
| 「T2 没开时，读屏端点**拿不到任何屏幕数据**，而且返回的是**同一个错误码**」 | 真机实测：**要么拿到数据（红了），要么拿到那个码** |

**所以这一阶段的每一条边界，都必须能写成一个「要么 X 要么红」的句子。**

---

## 二、四条边界

### 边界 1：默认关的三档，**关着时必须是「功能不存在」而不是「功能被拒绝」**

3.2 定了 T2/T3 默认关。**「关」的强度有两种，必须选强的那个：**

| 弱（不采用） | 强（采用） |
|---|---|
| 端点仍对外开放，内部判断后返回 `DISABLED` | **端点根本不注册**，调用返回 `404`/`UNKNOWN_ROUTE` |

**为什么必须选强的**：弱的那一种里，**「拒绝」是一个可以被绕过的判断**；
强的那一种里，**没有那条代码路径**。前者出错时表现为「答应了但不该答应」，
后者出错时表现为「明明开了却没反应」—— **后者的失败方式是安全的。**

> ⚠️ 但这与 3.3 的「协议兼容」有张力：`/app/*` 的兼容性要求端点名一致。
> **解法**：**兼容的是「开着的时候」**。关着时返回一个**明确且稳定**的错误码
> （不是 404 那种含糊的），并在契约表里逐条记下「关着时返回什么」。
> 这既保住了兼容，又保住了「没有那条路径」。

### 边界 2：**禁止以宿主自身为目标**（来自 3.2 ①-bis 的升级）

`mobile-pilot` 对 `app.launch` 只放行一种精确形状（只带宿主包名、且只用于把宿主叫回前台），
其余带宿主包名的调用一律拒。**升级成边界层的规则**：

> **任何操作都不许以宿主应用为目标**，唯一例外是被显式列出的那个「回到前台」形状。

**理由**：允许以宿主为目标 = 允许 agent **驱动它自己** = 一条权限自举回路。
**它是这一层里唯一一条「两个上游做法不同」的规则** —— DSHA 的桥的 `/app/launch?pkg=`
不区分目标是谁。**这是 DSHBox 更严的一处，值得吸收。**

### 边界 3：`/exec` 按通道分级，且**不许「有一个通道就行」**

3.2 已定 T3 要按 root / Shizuku / ADB 分别确认。3.4 要把这句话变成结构：

- **三个通道的授权状态必须分开存**，不是一个 `shellEnabled` 布尔；
- **调用时必须指明用哪个通道**，或者由核心按**用户已授的最小通道**选择；
- **升通道必须重新确认**：用户只给了 Shizuku，而某条命令需要 root ⇒ **拒绝，并说明为什么**，
  不是「悄悄升到 root」**也不是**「用一个更弱的通道跑一遍假装成功」。

> 最后那两句是这条边界真正的内容：**失败必须表现为「没做成」，不能表现为「做成了但用的不是你要的通道」**。

### 边界 4：**T4 不是「不给模型」，是「模型拿不到」**

3.2 写「T4 永不交给模型」。它的可检查形式是：

> **桥凭据不出现在**：任何工具的参数、任何工具返回的正文、任何日志行、任何错误消息。

**这一条本仓库已经吃过一次教训**（事故 41：真机导出的归档里 API Key 是明文，
而每一条门禁都绿）。所以它**必须有自己的检查**，不能只靠「注意不要打印」。

## 三、失败时的表现：**fail-closed，并且说清楚是哪一种失败**

| 情形 | 正确表现 |
|---|---|
| 授权状态读不到 / 损坏 | **拒绝**（不是当作「已开启」） |
| 端点不在 3.3 的子集里 | 拒绝，错误码**稳定** |
| 通道不可用 | 拒绝，并指出**该去开哪一个** |
| 调用可能已执行但结果不明 | **`EXECUTION_UNKNOWN`**，**要求先观察，不许重放** |

最后一条不是我们发明的 —— 上游的协议里就有这个词，而且它是对的：
**「可能执行了」和「执行了」必须可区分**，否则重试等于破坏。

---

## 四、这一阶段的验收 = **3.5 的清单**

每条边界的验收形式是**「关着的时候真的做不了」**，不是「开着的时候能用」。

| 边界 | 3.5 要验什么 | 通过判据 |
|---|---|---|
| **1** 默认关 | 在**没有**开启 T2/T3 的全新安装上，逐端点调用 | 每一条都返回那个**约定的关断错误码**，且**没有任何数据**返回 |
| **1** 开启后 | 打开 T2，再调同一批端点 | 行为改变；**关断时返回的码不再出现** |
| **2** 禁止自目标 | 用宿主包名调 `launch` | 拒绝，且**宿主没有变化**（前后前台应用相同） |
| **3** 通道分级 | 只授 Shizuku 时，调一条需要 root 的命令 | 拒绝，且**错误消息指出该去开哪个**；`id` 输出的 uid 未变化 |
| **4** 凭据不外泄 | 遍历全部工具参数/返回/日志，搜桥凭据 | **零命中** |

> ⚠️ **「关着时返回什么」必须写进 3.3 的契约表**，否则 3.5 没有可比对的期望值 ——
> **那就是一条没有输入空间的断言**（事故 30 的形态，本仓库栽过）。

---

## 五、这一阶段**不做**什么

- **不做界面**（3.3 的入口负责呈现，3.4 只给出「必须写在界面上的三句话」）。
- **不做权限申请的流程**（那是 Android 系统的事，我们只判断「有没有」）。
- **不做审计日志** —— 它有价值，但**没有证据说明它属于 3.4**。
  真要做得先回答「记什么、给谁看、存多久、进不进备份」。
  **把它列成候选，不列成任务。**
