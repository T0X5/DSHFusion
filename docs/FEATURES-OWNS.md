# 我们自己的东西 —— 逐条「为什么这不是抄的」

> 这份清单回答一个问题：**这个项目里，哪些东西是「吸收两个上游之后仍然属于自己」的？**
>
> 它的存在理由：用户 2026-10-16 说「感觉就是 fork 的 DSHBox 加一些 DSHA 的功能，更像二改作品」。
> `docs/PRODUCT-DIRECTION.md` 定了方向，`tools/measure-ownership.py` 给了数字（自写占比 9.78%），
> **而这一份回答「那 9.78% 到底是什么」。**
>
> ⚠️ **每一项都必须能说出「为什么不是抄的」**。说不出就不该列在这里 ——
> 因为列了而说不出，这份清单就变成了自我安慰。

## 判定标准

一条东西算「自己的」，要满足**至少一条**：

1. **两个上游都没有**（不是把 A 和 B 拼起来，是做出一件 A 和 B 都没做的事）
2. **上游有但接不上**（它的实现依赖它自己应用内部的子系统，拿不过来）
3. **上游有但是错的**（真实执行证明它不成立 —— 不是「我觉得不好」）
4. **上游有但解决的是另一个问题**（词汇/前提不同，照搬会静默失效）

---

## 一、两个上游都没有的

### 1.1 可验证性基础设施（本项目最大的差异化）

**335 项本机套件 · 176 条 :backup 测试 · 44 条事故记录 · 24+1 处偏离可重放 ·
逐字节导入溯源 · 产物级断言**

- **为什么不是抄的**：DSHBox 与 DSHA 都**没有**这一套。DSHBox 有常规单测与 CI，
  DSHA 有一批契约检查（而它的主干 CI 当前是**失败**的 —— 那是我们选 DSHBox 当骨干的理由之一）。
- **证据**：`tools/verify-phase0.sh`、`docs/INCIDENTS.md`、`governance/`。
- **它为什么算「东西」而不是「工程卫生」**：因为这 44 条事故里**每一条的注入都现场证明会红**，
  而「每一个新断言都要用一个真实注入的故障证明它真的会红」是本仓库的硬性方法论。
  一套能自我证伪的检查体系，是产品的一部分 —— 它决定了「改动能不能被信任」。

### 1.2 真机抓出的 6 个 bug 与它们的守卫

第 39–44 条（`PARENT_LINK` ×2 / `UNSAFE_MOVE` / API Key 明文进归档 / `OVERLAPPING_TARGETS` /
`merge` 写死）。**本机 176 条 + 335 项 + CI 全绿时一个都没抓到。**

- **为什么不是抄的**：这 6 个都是**我们自己的代码**的 bug，上游没有对应的东西可抄。
- **它们留下了什么**：`DshHostPaths`（统一路径规范化）、`DESTINATION_IS_ARTIFACT`、
  `DshCredentialsSource`（树内选择性投影）、`OVERLAPPING_MEMBERS`（导出时就拒绝嵌套成员）、
  `merge` 按「根是不是整个 home」推导 —— **每一条都配了会红的测试**。

## 二、上游有但接不上的

### 2.1 `DshCredentialsSource` —— 树内选择性投影

- **上游有的**：`CredentialFileBackupSource`，它做同一件事。
- **为什么接不上**：它硬性要求「源里只有一个文件、路径为空」，只能套在**根就是凭据文件**的源上。
  而那样凭据文件就成了**独立的根** —— 上游 `HostDataTransaction` 用路径前缀判目标重叠，
  直接抛 `OVERLAPPING_TARGETS`（**真机第 43 条**）。
- **我们做的**：包在**整棵树**外面，只对那一个文件动手、其余原样透传。**根的数量不变 ⇒ 目标不重叠。**

### 2.2 `HostRestoreMapping` —— 落点映射

- **上游有的**：`NativeRestoreTargets`。
- **为什么接不上**：它第一句就是 `BackupJson.string(root, "logicalKind")`，认 `dsh-home`/`dsh-child`；
  而我们的归档根只有 `id`/`scope`/`external` —— **两套词汇，不是同一套的两个实现**（它会直接抛）。
- **我们做的**：一个成员一个 group，`mergeSubdir` 由 `path` 推导（少一个来源就少一类分叉）。

### 2.3 `DshAutomaticBackupRetention` —— 保留策略

- **上游有的**：`AutomaticBackupPruner`。
- **为什么接不上**：它的删除判据建立在「自动备份是**一个目录 + 四个具名成员**」上
  （`Set.of("portable.dshbak","verified.json","operation.json","source-checks")`），
  而我们的产物是**单文件** `DSHDATA` 容器 —— 直接抄不是「命名对不上」，
  是**连输入都没有**，后果是**静默的空操作**（用户以为保留 3 份，磁盘无限增长）。
- **我们做的**：自写保留策略，**只碰 `MAINTENANCE`**（手动/救援永不入候选）、
  不完整的 `PARTIAL`/`BEST_EFFORT` **既不计数也不删而且要报出来**、`keep < 1` 按 1 处理。
- **可证伪的形式**：`upstreamPrunerJudgementMatchesNothingOfOurs` 把上游那段判据
  跑在我们的真实产物名上，断言一份都删不掉，**同时**断言我们的策略确实会删 ——
  否则那条用例证明的只是「两边都不删」。

### 2.4 自动备份的调度与界面

- **上游有的**：`AutomaticBackupService`（4 个 android import）、`AutomaticBackups`（6 个）。
- **为什么接不上**：它们挂在 DSHA 自己的 `HarnessController` / SharedPreferences 门面上；
  而我们的要挂在自己的 `applicationContext` 与 `userDataDir` 上。
- **我们做的**：`AutomaticBackupJobService` + `AutomaticBackupSettingsStore` + 设置界面，
  用**平台自带的 `JobScheduler`**（不引入新依赖）。

## 三、上游有但是错的（真实执行证明）

### 3.1 凭据投影从来没接上生产路径

- **上游有的**：`CredentialProjection` + `CredentialFileBackupSource`，逻辑是对的、单测也过。
- **错在哪**：**生产路径上没有任何人用它**（全库只被它自己的单测引用）。
  于是真机上 `.credentials.yaml` **原样**进了归档 —— 用户的 API Key 与浏览器会话授权
  明文躺在下载目录里（**技术事故第 41 条**）。
  而排除清单里那条 `.dsh/credentials` 与真机文件名 `.credentials.yaml` **不是同一个东西**。
- **我们做的**：按**路径**判断、**无条件**包上投影（不靠调用方传标志位）；
  排除清单**改成引用常量**（`CredentialProjection.FILE`），两处不可能再各写一份。

### 3.2 「更新失败自动回滚」那条 ✅ 是错报的

- **我们曾声称**：阶段 2 的验收标准「覆盖更新失败 → 自动回切」达标。
- **实际**：那个 ✅ 的依据是**恢复**事务的回切测试 —— **验的是另一个东西**。
  而「受管更新」根本没做（18 个未搬的 DSHA 类里有 4 个是更新事务）。
- **现在**：定为 **阶段 2.8**，见 `docs/PHASE2.8-MANAGED-UPDATE.md`。

### 3.3 §8.8「窄范围会静默多恢复」也是错报的

- **我们曾声称**：选「只恢复会话」+ 全量归档 → 设置与插件也会被恢复进去。
- **实际**：`NativeRestorePlan.inspect` 会把那个根**跳过**，抛 **`NO_RECOVERABLE_SCOPE`**，
  **数据一动不动**。由测试 `aNarrowScopeRefusesAFullArchiveInsteadOfOverRestoring` 用执行证明。
- **教训**：**我推理了一个行为，写成了限制 —— 而推理不是证据。**

## 四、身份

### 4.1 全量包名收回（阶段 3.0）

`com.dshbox.app` → `com.dshfusion.app`，**279 个文件 / 1069 处 / 52 个目录**。

- **为什么算自己的**：它让「上游文件」与「我们的文件」**在包名上就分得开** ——
  这是「边界是自己的」可检查的前提。没有它，`measure-ownership.py` 那种分类只能靠路径猜。
- **代价如实登记**：同步上游时这条偏离会失败（上游带来的文件又是旧包名），
  需要**人工重跑重命名工具**，见 `DIV-0025`。

## 五、这个清单该怎么用

- **每完成一件「自己的东西」，加一条进来**，并写清属于上面哪类（1/2/3/4）。
- **说不出「为什么不是抄的」的，不要写进来。**
- `tools/measure-ownership.py` 给的是**比例**；这一份给的是**内容**。两者缺一不可 ——
  只看比例会为了数字而堆代码，只看内容会不知道整体在往哪走。

## 已知的诚实边界

- **自写占比只有 9.78%**（按行数）。这个数字不因为这份清单而变大 ——
  它衡量的是 Kotlin/Java 行数，而**本文件、`tools/`、`governance/` 都不在其中**。
- **本清单里 1.1（可验证性）与 1.2（真机 bug 守卫）不是用户能直接看到的功能**。
  它们是**产品的一部分**（决定了改动可不可信），但**不是「用户会夸」的那种东西**。
  真正会让这个项目「不像二改」的，是**阶段 3.1–3.5 的统一设备能力层** —— 那是用户选的方向。
