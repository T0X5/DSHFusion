# 阶段 3.2：授权模型（**能力分级**）

> **它的输入全部来自 3.1 台账的「前提」列，不是来自任何上游 README。**
> 见 [PHASE3.1-CAPABILITY-LEDGER.md](PHASE3.1-CAPABILITY-LEDGER.md)（第一至第五批）。
>
> **它的输出是 3.4（安全边界）的直接输入**：每一档的默认策略。
> **它是 3.3（统一入口）的派发依据**：用户授权的是**档**，不是**单个端点**。

---

## 一、为什么要分级，而不是逐条开关

3.1 查完之后有一件事很刺眼：**11 条能力的「前提」差别极大**，
但它们在上游的实现里**长着同一张脸** —— 都是「一个 HTTP 端点」或「一个工具名」。

| 同脸的 | 实际前提 |
|---|---|
| `ui.notify.turn-end` | 通知权限（一次授权，低风险） |
| `agent.auto-review` | 无（纯本地判断） |
| `device.shell.command` | **root / Shizuku / ADB 三选一**（能做的远多于它说的） |
| `ui.a11y.drive` | **无障碍服务**（可读屏 + 代用户操作） |

**「长得一样」是设计的失败，不是便利。** 一个逐条开关的授权模型会让用户
在 11 个形状相同的复选框面前做 11 次无从判断的选择 ——
而**其中三条一旦给错，等于把手机交出去**。

> **所以分级的判据不是「这个功能是什么」，而是「它错了之后最坏能做什么」。**

---

## 二、五档模型

档位按**最坏后果**排，不按功能排。

| 档 | 名字 | 最坏能做什么 | 判据（可检查） |
|---|---|---|---|
| **T0** | 无前提 | 只影响它自己 | 不读设备状态、不写设备、不发起外部请求 |
| **T1** | 应用层权限 | 打扰用户 | 只需要一个 Android **运行时权限**（通知 / 悬浮窗 / 闹钟） |
| **T2** | 无障碍 | **看见屏幕 + 代替用户点** | 需要 `BIND_ACCESSIBILITY_SERVICE`，或经此路径读屏/注入输入 |
| **T3** | 提权 | **以 shell 身份做任何事** | 需要 Shizuku / root / ADB 中至少一条通道 |
| **T4** | 桥凭据 | **完全接管整座桥** | 能读到桥的鉴权凭据（`X-Token`）本身 |

### 为什么 T2 排在 T3 前面（T2 比 root 更该警惕）

这条反直觉，但它有实测依据：

- **root 通道是有边界的**：3.1 实测的那座桥对 root 也照样拦
  （`[POLICY_BLOCKED]`「root 和旧确认开关不能放行」，见 `/app/help` 原文）。
- **无障碍没有这样的边界**：它能读到你**正在看的每一屏**，包括密码框、
  验证码、聊天记录；也能**代替你点**「允许」。
  也就是说 —— **它不是「更大的权限」，它是「一个新的你」。**

> **所以 T2 的提示语不能说「读取屏幕内容」，要说「看到你屏幕上的任何内容，并代替你操作」。**
> 这不是修辞，是 3.4 里那条默认策略的依据。

## 三、台账 11 条逐条归位

| `id` | 实测前提 | 档 |
|---|---|---|
| `safety.destructive-guard` | 无（拦截器，不碰设备） | **T0** |
| `agent.auto-review` | 无（官方包，默认关） | **T0** |
| `ui.mobile-adaptation` | 无（前端适配） | **T0** |
| `ui.notify.turn-end` | 通知权限 | **T1** |
| `ui.overlay.status` | 悬浮窗权限 | **T1** |
| `device.alarm` | 闹钟（应用层） | **T1** |
| `device.app.control` | 应用层 —— ⚠️ 见 §五 未决① | **T1（暂定）** |
| `ui.a11y.drive` | 无障碍服务 | **T2** |
| `device.computer-use` | 桥凭据 + 读屏/点击（走无障碍） | **T3**（凭据档） |
| `device.vdisplay` | 桥凭据 + 虚拟屏 | **T3**（凭据档） |
| `device.shell.command` | root / Shizuku / ADB | **T3**（三档前提） |

> **T4 目前是空的**：今天没有任何一条能力**应该**把桥凭据交给模型。
> `computer-use` / `vdisplay` 只是**客户端**用凭据 —— 那是实现细节，不该成为能力。
> **T4 保留为空档，是因为它必须存在**：3.3 自己会持有凭据，
> 而「持有它就等于接管整桥」这件事（DSHA 源码原话）必须在模型里有一格。

## 四、每一档的默认策略（**3.4 的直接输入**）

| 档 | 默认 | 授权粒度 | 撤销成本 |
|---|---|---|---|
| **T0** | **开** | 无（没有可授的） | — |
| **T1** | **开，但首次使用时问一次** | 每项一次 | 随时关 |
| **T2** | **关**（必须显式开） | 每项一次，**并要求在系统设置里也已经开** | 随时关 |
| **T3** | **关**，且**每一档前提单独确认** | **按通道**（root / Shizuku / ADB 分别）+ 每次高危操作再确认 | 随时关 |
| **T4** | **永不交给模型** | 不提供授权入口 | — |

三条**理由必须写在界面上**，否则用户只会看到「允许/拒绝」：

1. **T2 默认关** —— 见 §二「它是新的你」。
2. **T3 按通道分别确认** —— 因为三档的**后果不同**：
   Shizuku 只在你授予它的范围内；root 是全机；ADB 要连着线。
   **把它们合并成一个开关，就是把最弱的那个的风险灌到最强的那个上。**
3. **T4 永不开放** —— 桥凭据是**进程身份**，不是**用户偏好**。

## 五、未决问题（下一批）

### ① `device.app.control` 到底是不是 T1

它只需要应用层，但「启动任意应用」+「列出全部应用」在 Android 上
**需要 `QUERY_ALL_PACKAGES` 或等价的可见性声明** —— 那是商店审核意义上的敏感项，
且**能列出用户装了什么**（这本身是隐私）。

**要查的是**：DSHBox 的 `mobile-pilot` 用的是哪条路径、它声明了什么。
**没查之前不许定档** —— 定档就是一个承诺。

### ② T3 的三档前提，能不能在同一个模型里表达

`device.shell.command` 是**三选一**，而我的五档是**单值**。
两种做法：
- **T3a / T3b / T3c** 三个子档（更准，但会把档位表撑大）；
- **T3 带一个「可用通道集合」字段**（更紧凑，但「集合」容易退化成「有一个就行」）。

**倾向前者**：档位的价值在于**互斥且可比较**；用集合表达会在 UI 上退化成勾选框。

### ③ 授权状态存在哪

它必须**不进备份归档**（否则「换台设备恢复」会把授权一起搬过去 ——
而授权是**这台设备**对**这台设备**的信任）。
这一条与 [PRODUCT-DIRECTION §8](PRODUCT-DIRECTION.md) 的桥凭据排除是同一个坑，
**要复用同一个机制**（`DshBackupExclusions`），不要新造一份。
